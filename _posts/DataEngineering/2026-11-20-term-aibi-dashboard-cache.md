# 0. 이 글을 읽기 전에

"데이터를 갱신했는데 대시보드 숫자가 그대로"인 경우의 가장 흔한 원인입니다. **쿼리 결과 캐시**(테이블이 바뀌면 무효화)와 **성격이 다릅니다.**

# 1. 한 줄 정의

AI/BI 대시보드는 로딩 시간을 줄이기 위해 **24시간 결과 캐시**를 유지합니다. **최선 노력(best-effort)** 방식이고, **기저 데이터가 바뀌어도 자동으로 무효화되지 않습니다.**

# 2. 동작 방식

- 대시보드는 **먼저 대시보드 캐시**를 확인하고, 없으면 **일반 쿼리 결과 캐시**를 확인합니다. 둘 다 없을 때 SQL 웨어하우스에서 쿼리를 실행합니다.
- 대시보드 자격 증명과 연결된 **과거 쿼리 결과**를 활용하며, 캐시를 만들거나 유지하지 못하는 경우도 있습니다. 캐시 데이터에는 **메모리 한도나 고정된 쿼리 수 제한이 없습니다.**
- 캐시에서 결과를 제공하면 **SQL 웨어하우스가 실행 중일 필요가 없습니다.** 웨어하우스는 캐시가 제공하지 못하는 쿼리를 실행할 때만 시작됩니다.

# 3. 두 캐시의 무효화 차이 (핵심)

| | 쿼리 결과 캐시 | 대시보드 캐시 |
|---|---|---|
| 데이터가 바뀌면 | **모든 항목이 무효화** | **자동 무효화·갱신 안 됨** |
| 오래된 데이터 반환 | **하지 않음** | **최대 24시간 지난 결과**를 반환할 수 있음 |
| 갱신 방법 | 자동 | **대시보드 스케줄** |

- 24시간 이내에 가져온 결과는 **그 뒤에 데이터가 바뀌었어도** 캐시된 결과를 사용합니다.
- **파이프라인 단계에서 데이터를 갱신한다고 해서** 대시보드 캐시가 갱신되지는 않습니다. **스케줄 갱신을 제외하면** 캐시가 제공하지 못하는 쿼리를 대시보드가 실행할 때만 캐시가 갱신됩니다.

# 4. 캐시 단위: 공유 vs 사용자별

| 대시보드 유형 | 캐시 |
|---|---|
| **공유 데이터 권한**으로 게시 | **공유 캐시** — 모든 뷰어가 같은 결과 |
| **초안**이거나 **개별 데이터 권한**으로 게시 | **사용자별 캐시** — 뷰어의 데이터 권한에 따른 결과 |

# 5. 파라미터·필터와 데이터셋 크기

- 대시보드에 **파라미터**를 적용하면, **24시간 이내에 같은 파라미터를 썼던 경우가 아니면 쿼리가 다시 실행**됩니다. (파라미터는 쿼리에 값을 직접 치환하므로 쿼리 기록에 항상 남음)
- 데이터셋이 **100,000행 초과**이면 필터를 적용할 때, **24시간 내 같은 필터를 쓴 적이 없다면 쿼리가 다시 실행**됩니다.

| 데이터셋 크기 | 처리 |
|---|---|
| **작음 (≤ 100K행, ≤ 100MB)** | 초기 로딩 후 **브라우저에서** 필터·집계. 웨어하우스에 추가 요청이 없어 **쿼리 기록에 남지 않음** |
| **큼 (> 100K행 또는 > 100MB)** | **백엔드**에서 처리. 초기 데이터셋 쿼리가 SQL `WITH`절로 감싸져 쿼리 기록에 남음 |

- 잘려서 표시되는 표를 CSV로 **다운로드**하면 **웨어하우스에 쿼리**가 실행됩니다.
- **여러 페이지 대시보드**: 초안을 편집하면 **모든 데이터셋을 로드·캐시**하고, 게시된 대시보드는 열린 페이지에 필요한 데이터셋만 실행·캐시합니다. **스케줄이 있으면 모든 데이터셋이 스케줄대로 갱신**되고 결과가 캐시됩니다.

# 6. 시간 함수

`current_timestamp()` 또는 비슷한 함수를 쿼리에 쓰면 **대시보드 수준 캐시는 무효화되지 않지만**, **쿼리 결과 캐시는 무효화**되어 캐시 갱신을 유발합니다.

# 7. 신선도를 높이는 방법

1. **대시보드 스케줄**을 건다. 공유 데이터 권한으로 게시한 대시보드에 스케줄을 걸면 **모든 뷰어의 초기 로딩이 크게 빨라지고**, 스케줄 실행은 데이터셋 SQL을 돌려 **쿼리 결과 캐시를 채웁니다.**
2. 결과를 **미리 계산해 저장**하려면 **데이터셋 구체화(dataset materialization)** 를 사용합니다.
3. 신선도 요구가 24시간보다 짧다면 **오래된 결과가 보일 수 있음을 전제로 설계**합니다.

# 8. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "데이터를 갱신하면 대시보드도 바로 최신" | **자동 갱신 안 됨**, 최대 24시간 지난 결과 가능 |
| "ETL 마지막에 데이터를 갱신하면 대시보드 캐시도 갱신" | **갱신되지 않음.** 스케줄이 필요 |
| "대시보드 캐시도 7일" | **AI/BI 대시보드는 24시간**, 7일은 SQL UI cache |
| "캐시가 있으면 항상 웨어하우스가 켜진다" | 캐시 적중 시 **웨어하우스가 시작되지 않음** |
| "누구나 같은 결과를 본다" | 공유 권한이면 **공유 캐시**, 초안·개별 권한이면 **사용자별 캐시** |

# 9. 한 줄 정리

- AI/BI 대시보드 캐시 = **24시간·최선 노력**의 결과 캐시. 먼저 **대시보드 캐시 → 쿼리 결과 캐시** 순으로 확인한다.
- **데이터가 바뀌어도 자동 무효화되지 않아** 최대 24시간 지난 값이 보일 수 있다. **스케줄**로 갱신한다.
- **공유 데이터 권한이면 공유 캐시**, 그렇지 않으면 **사용자별**. 캐시가 적중하면 **웨어하우스가 켜지지 않는다.**
