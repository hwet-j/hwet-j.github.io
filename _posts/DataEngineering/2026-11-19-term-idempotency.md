# 0. 이 글을 읽기 전에

멱등성은 Databricks 전용 용어가 아니라 **분산 시스템·API·데이터 파이프라인 전반**에서 쓰는 일반 개념입니다. 이 글은 Databricks 문서가 이 개념을 언급하는 부분(Repair run)을 근거로 데이터 적재에 적용하는 방법을 설명합니다.

# 1. 한 줄 정의

같은 작업을 **한 번 실행하든 여러 번 실행하든 결과가 같은** 성질입니다.

# 2. 쉬운 비유 두 가지 (이해를 돕기 위한 비유)

- **엘리베이터 버튼**: 5층 버튼을 한 번 누르든 열 번 누르든 결과는 "5층으로 간다"로 같습니다 → 멱등.
- **계좌 이체**: "잔액을 100원 **늘린다**"를 두 번 실행하면 200원이 늘어납니다 → **비멱등**. "잔액을 1,000원으로 **설정한다**"는 몇 번을 해도 1,000원입니다 → 멱등.

핵심 감각: **"~를 더한다(추가)"는 비멱등, "~로 만든다(설정/교체)"는 멱등**인 경우가 많습니다.

# 3. 왜 데이터 파이프라인에서 중요한가

파이프라인에서는 **같은 작업이 여러 번 실행되는 일이 일상적**입니다.

| 상황 | 같은 작업이 다시 실행되는 이유 |
|---|---|
| 자동 재시도 | 일시 오류로 실패 후 재시도 |
| **Repair run** | 실패한 task를 사람이 다시 실행 |
| 스케줄 중복 | 이전 실행이 길어져 겹치거나 수동으로 한 번 더 실행 |
| 장애 복구 | 어디까지 처리됐는지 모를 때 안전하게 처음부터 재실행 |
| 오류 정정 | 원천 데이터 수정 후 같은 기간 재적재 |

**멱등하지 않으면 재실행할 때마다 데이터가 중복**되어 건수·합계가 틀어집니다. 멱등하면 재실행은 **언제나 안전한 선택지**가 되어 운영이 단순해집니다.

# 4. Databricks 문서의 경고

공식 문서(Repair)는 이렇게 말합니다. (의역)

> Lakeflow Jobs는 task를 멱등하게 만들어 주지 않는다. task가 실패하기 전에 출력의 일부를 이미 썼다면, 다시 실행할 때 **그 데이터가 중복될 수 있다.** repair가 안전한지는 task 자체의 로직에 달려 있으므로, 재실행 전에 각 task가 무엇을 쓰는지 검토하고, 중복이 문제라면 **append 대신 overwrite나 merge 같은 멱등한 연산**을 사용하라.

즉 **재실행 기능은 제공되지만, 안전한 재실행은 사용자가 보장해야 합니다.**

# 5. 쓰기 방식별 멱등성

| 쓰기 방식 | 같은 작업을 2번 실행하면 | 멱등? | 비고 |
|---|---|---|---|
| `append` | 같은 행이 **또 추가**됨 | ❌ | 가장 흔한 중복의 원인 |
| `DELETE` 후 `append` (커밋 2번) | 끝까지 성공하면 동일하나, **중간 실패 시 빈 구간** | △ | 완주하면 같지만 실패 시 위험 |
| **`replaceWhere`** (커밋 1번) | 같은 범위를 같은 데이터로 **교체** | ✅ | 실패 시 기존 데이터 유지 |
| 전체 `overwrite` | 매번 테이블 전체를 교체 | ✅ | 범위가 전체일 때만 |
| **`MERGE`** (키 기준) | 같은 키는 갱신, 새 키만 삽입 | ✅ (조건부) | 키가 **유일/안정적**이어야 함 |
| `REPLACE USING` | 지정 키가 같은 행을 교체 | ✅ | 빈 소스에서 삭제 안 함 |

## 눈으로 보는 비교: 같은 1월 청크를 두 번 실행했을 때

```
초기: 1월 행 100개

[append]       1차 실행 → 1월 200개 (기존 100 + 새 100)  ❌
               2차 실행 → 1월 300개                       ❌ (점점 늘어남)

[replaceWhere] 1차 실행 → 1월 100개 (교체)               ✅
               2차 실행 → 1월 100개 (같은 결과)          ✅
```

```python
# 비멱등: 재실행하면 2026-01 이 두 배가 됨
df_jan.write.mode("append").saveAsTable("main.l0.orders")

# 멱등: 몇 번 돌려도 2026-01 은 한 벌
(df_jan.write.mode("overwrite")
   .option("replaceWhere", "order_dt >= '2026-01-01' AND order_dt < '2026-02-01'")
   .saveAsTable("main.l0.orders"))
```

# 6. 멱등성을 깨뜨리는 흔한 함정

## 6-1. 재실행마다 값이 달라지는 컬럼

```python
df = df.withColumn("load_dttm", F.current_timestamp())   # 실행할 때마다 값이 다름
df = df.withColumn("row_uuid", F.expr("uuid()"))          # 실행할 때마다 값이 다름
```

- "결과가 같다"를 **행의 비즈니스 값** 기준으로 볼지, **모든 컬럼** 기준으로 볼지 정해야 합니다.
- 보통 `load_dttm` 같은 적재 시각은 재실행마다 달라도 괜찮다고 보지만, **키(PK)나 중복 판단에 쓰는 컬럼**이 비결정적이면 `MERGE`/중복 제거가 깨집니다.

## 6-2. 소스에 같은 키가 중복

`MERGE`는 **소스에서 같은 키가 여러 행**이면 어떤 행을 쓸지 모호해서 오류가 나거나 의도와 다르게 동작할 수 있습니다. 소스를 키 기준으로 먼저 **중복 제거**하세요.

## 6-3. 외부 부작용

DB에 쓰는 것 외에 **메일 발송, 외부 API 호출, 파일 업로드**가 같이 있다면, 재실행 시 한 번 더 일어납니다. 이런 작업은 **요청 ID(멱등 키)** 를 만들어 "이미 처리했는지" 확인해야 합니다.

## 6-4. 부분 쓰기 + 재실행

task가 **여러 곳에 순서대로** 쓰는 구조에서 중간에 실패하면, 이미 쓴 곳과 아직 못 쓴 곳이 섞인 상태가 됩니다. 각 쓰기를 멱등하게 만들거나, 쓰기를 하나의 원자적 단위(`replaceWhere`, `BEGIN ATOMIC`)로 묶습니다.

# 7. 멱등한 적재를 만드는 방법 (선택 가이드)

```
쓰려는 범위가 "조건으로 명확히 정해지는가"? (예: 월/일 구간)
 ├─ 예 → replaceWhere            ← 이 시리즈의 적재 패턴
 └─ 아니오 (키로 갱신/삽입)
        ├─ 키가 유일·안정적 → MERGE 또는 REPLACE USING
        └─ 키가 없다 → 키를 만들 방법(자연키/해시)을 먼저 설계
항상: 소스 중복 제거, 비결정 값 확인, 외부 부작용에 멱등 키
```

# 8. 멱등성 테스트 방법

가장 확실한 방법은 **같은 작업을 두 번 실행하고 결과를 비교**하는 것입니다.

```sql
-- 1차 실행 후
SELECT COUNT(*) AS cnt, SUM(amount) AS amt
FROM main.l0.orders
WHERE order_dt >= '2026-01-01' AND order_dt < '2026-02-01';

-- 2차 실행(같은 작업 재실행) 후 위 쿼리를 다시 실행 → 값이 같아야 함
```

- 행 수뿐 아니라 합계·체크섬(`SUM(HASH(...))` 등)도 비교하면 더 확실합니다.
- **일부러 실패시킨 뒤** 재실행해도 같은 결과가 되는지 확인하세요. (실패 → 재실행 시나리오가 실제 위험 지점)

# 9. 체크리스트

- [ ] 이 task를 두 번 돌리면 **중복이 생기는가?**
- [ ] 중간에 실패했다가 다시 돌리면 **어떤 상태**가 되는가?
- [ ] 같은 입력에 **항상 같은 출력**이 나오는가? (비결정 함수, 정렬 순서 의존)
- [ ] `append`를 쓰고 있다면 **정말 필요한가**? (replaceWhere/MERGE로 대체 가능한가)
- [ ] 외부 부작용(메일·API)에 **멱등 키**가 있는가?
- [ ] Repair/재시도가 일어나도 **안전하도록** 테스트했는가?

# 10. 한 줄 정리

- 멱등성 = **여러 번 실행해도 결과가 같은 성질**. "더한다"는 비멱등, "~로 만든다"는 대체로 멱등.
- 파이프라인에서는 재시도·repair·재적재가 일상이므로 **멱등하지 않으면 중복**이 생긴다.
- Databricks는 **repair 시 task의 멱등성을 보장하지 않는다**고 명시한다. `append` 대신 **overwrite/merge**를 쓰라고 권장한다.
- 이 시리즈의 해법: 청크별 **`replaceWhere`** (원자적 + 멱등).
