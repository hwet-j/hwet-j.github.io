# 0. 이 글을 읽기 전에

**컴퓨트 플레인(Classic vs Serverless)** 글을 먼저 읽으면 좋습니다. NCC는 **서버리스** 컴퓨트에서 내 리소스로 접속할 때의 네트워크를 다루는 설정입니다. (AWS 문서 기준)

# 1. 한 줄 정의

**NCC(Network Connectivity Configuration)** 는 서버리스 컴퓨트가 내 리소스에 연결하는 방식을 관리하는 **계정 수준·리전 단위의 구성 객체**로, 특히 **private endpoint(비공개 연결 지점)의 생성을 관리**합니다.

# 2. 왜 필요한가

서버리스는 Databricks 관리 영역에서 실행되므로, **내 VPC 안의 서버(DB, 파일 서버 등)에는 기본적으로 공인 IP로 접속**합니다. 내 리소스를 공인망에 열고 싶지 않다면 **Private Link**로 비공개 연결을 만들어야 하는데, 이 연결 정의를 NCC가 담습니다.

```
Serverless 컴퓨트 ──(private endpoint rule)──► VPC endpoint ──► 내 VPC의 NLB ──► 내 리소스
                       NCC 안에 정의                                  (공인망을 거치지 않음)
```

# 3. 핵심 개념

| 용어 | 설명 |
|---|---|
| **NCC** | 계정 단위·**리전별** 구성. 여러 워크스페이스에 붙일 수 있음 |
| **Private endpoint rule** | NCC에 추가하는 규칙. "이 도메인(FQDN)으로 가는 서버리스 트래픽은 이 private endpoint로 비공개 전송" |
| **연결 승인** | 규칙을 만든 뒤 **리소스(서비스) 쪽에서 연결 요청을 승인**해야 사용 가능 |
| **상태 ESTABLISHED** | 승인되어 연결이 확립된 상태. 이때부터 규칙이 유효 |
| **워크스페이스에 연결(attach)** | NCC를 같은 리전의 워크스페이스에 붙이면 NCC의 모든 규칙이 그 워크스페이스에 적용 |

# 4. 설정 흐름 (AWS, VPC 안의 리소스에 비공개 접속)

공식 문서의 흐름을 요약하면 다음과 같습니다.

1. **내 VPC에 Network Load Balancer(NLB)** 를 만들고(internal), 대상 리소스로 트래픽을 보내게 함
2. NLB를 노출하는 **VPC endpoint service**를 만들고, **엔드포인트 수락이 필요하도록(Acceptance required)** 설정
3. 계정 콘솔에서 **NCC를 만들고(워크스페이스 리전과 일치)**, **Private endpoint rule**에 VPC endpoint service 이름과 **대상 리소스의 FQDN**을 입력
4. AWS 콘솔에서 **엔드포인트 연결 요청을 승인**
5. NCC 화면에서 규칙의 상태가 **ESTABLISHED**인지 확인
6. NCC를 **워크스페이스에 연결**

# 5. 요구사항과 제한 (공식 문서)

- 워크스페이스가 **Enterprise 플랜**이고, **계정 관리자**여야 합니다.
- 계정당 리전별 **NCC 최대 20개**, 리전당 **private endpoint 30개**(NCC들에 분배), NCC 하나에 **워크스페이스 최대 50개**
- private endpoint rule 하나당 **도메인 이름 최대 100개**
- **와일드카드 도메인**(`*.example.com`) 불가. FQDN으로 명시
- **DNS chasing, DNS redirect 미지원**: 모든 도메인 이름이 **백엔드 리소스로 직접 해석**되어야 함
- 교차 리전: VPC endpoint service가 **최소 2개 가용 영역**에 있어야 하고, 소비자 리전을 엔드포인트 서비스 구성에 추가해야 함
- 서버리스 → 고객 리소스 연결은 **IPv4**만 지원
- 이 비공개 연결 기능은 **시간당 private endpoint 요금과 처리 데이터(GB)당 요금**이 청구됩니다. (일부 Databricks private connectivity 기능은 private preview이며 계정 팀을 통해 접근 가능)
- 네트워크 연결은 서버리스 → 내 VPC 리소스 방향입니다. **RDS 다중 AZ처럼 IP가 바뀌는 대상은 NLB 대상 그룹의 IP 동기화**가 필요할 수 있다고 안내합니다.

# 6. 예전의 "NCC stable IP"는 어떻게 되었나

공식 문서에 따르면 **Public Preview 때 NCC UI/API로 제공하던 "legacy stable IP" 목록은 폐기(decommission)** 되어 더 이상 NCC UI나 API로 제공되지 않습니다. 이 IP를 방화벽에 등록해 쓰고 있었다면 **새 방식(서버리스 아웃바운드 IP 게시 파일)으로 이전**해야 하며, 이전 전에는 서버리스가 리소스에 접근할 때 **403 Forbidden**이 날 수 있습니다. (→ 서버리스 아웃바운드 IP 글)

# 7. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "NCC를 만들면 바로 비공개 연결이 된다" | private endpoint 규칙 + **리소스 쪽 승인** + 상태 **ESTABLISHED**가 필요 |
| "NCC는 워크스페이스마다 따로 만든다" | **계정·리전 단위**. 같은 리전 워크스페이스 여러 개에 연결 가능 |
| "NCC가 Classic 컴퓨트에도 적용된다" | NCC는 **서버리스** 연결용 |
| "IP로 지정해서 연결한다" | **FQDN** 기준(와일드카드 불가) |
| "온프레미스 서버에도 바로 쓸 수 있다" | VPC의 **NLB 뒤 리소스** 기준. 온프레미스는 VPC까지의 경로(전용선/VPN 등)가 별도로 필요 |

# 8. 한 줄 정리

- NCC = **서버리스 → 내 리소스** 비공개 연결을 정의하는 **계정·리전 단위 설정**.
- 구성: **NLB + VPC endpoint service → NCC의 private endpoint rule(FQDN) → 승인 → ESTABLISHED → 워크스페이스에 연결**.
- 제한(NCC 20개/리전, 엔드포인트 30개/리전, 도메인 100개, 와일드카드·DNS redirect 불가)과 **비용**에 유의.
- 예전 **stable IP는 폐기**되었다.
