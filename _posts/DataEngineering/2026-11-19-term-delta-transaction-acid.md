# 0. 이 글을 읽기 전에

이 글은 "Spark로 데이터를 쓰다가 일부만 실패했는데 왜 **아무것도** 저장되지 않았지?"라는 의문에서 출발합니다. 답은 **Delta Lake의 트랜잭션 구조**에 있습니다. 데이터베이스(Oracle, MySQL 등)의 트랜잭션을 아시면 이해가 빠르지만, 몰라도 괜찮게 처음부터 설명합니다.

# 1. 한 줄 정의

Delta Lake는 쓰기 작업을 **"전부 반영되거나, 전혀 반영되지 않거나"** 둘 중 하나로만 끝나게 보장합니다. 이 성질을 **원자성(Atomicity)** 이라고 하고, 원자성을 포함한 네 가지 보장을 묶어 **ACID**라고 부릅니다.

# 2. 먼저 알아야 할 배경: Delta 테이블은 "파일 + 로그"

Delta 테이블은 DB의 테이블처럼 하나의 덩어리가 아니라, 크게 두 가지로 이루어져 있습니다.

```
클라우드 스토리지(S3, ADLS 등)
 └─ orders/                       ← 하나의 Delta 테이블
     ├─ part-0001.parquet         ← 데이터 파일 (실제 행들)
     ├─ part-0002.parquet
     ├─ part-0003.parquet
     └─ _delta_log/               ← 트랜잭션 로그 (어떤 파일이 "유효"한지 기록)
         ├─ 00000000000000000000.json   (버전 0)
         ├─ 00000000000000000001.json   (버전 1)
         └─ ...
```

- **데이터 파일**: 행이 저장된 Parquet 파일들. 한 번 쓰면 수정하지 않는 것이 기본입니다.
- **트랜잭션 로그**: "이 테이블의 현재 상태는 어떤 파일들로 이루어져 있다"를 **버전 단위로 기록**한 장부입니다.

공식 문서도 이렇게 설명합니다. "테이블의 현재 상태는 트랜잭션 로그에 유효하다고 표시된 모든 데이터 파일로 구성된다." 즉, **디렉터리에 파일이 있다고 해서 테이블의 일부인 것이 아닙니다. 로그에 적혀 있어야 테이블의 일부입니다.**

> 위 디렉터리 그림은 이해를 돕기 위한 개념도입니다. 실제 파일명과 구조는 다를 수 있습니다.
{: .notice--info}

# 3. ACID 네 글자를 쉬운 말로

| 글자 | 이름 | 공식 문서의 정의 | 쉬운 설명 |
|---|---|---|---|
| A | Atomicity (원자성) | 트랜잭션은 완전히 성공하거나 완전히 실패한다 | 송금할 때 "출금만 되고 입금은 안 된" 상태가 없다 |
| C | Consistency (일관성) | 동시 작업이 데이터의 특정 상태를 어떻게 관찰하는가 | 읽는 사람이 항상 "말이 되는" 상태를 본다 |
| I | Isolation (격리) | 동시 작업끼리 어떻게 충돌할 수 있는가 | 여러 작업이 동시에 돌아도 서로 망치지 않는다 |
| D | Durability (지속성) | 커밋된 변경은 영구적이다 | 성공 응답을 받은 데이터는 사라지지 않는다 |

공식 문서는 "많은 기술이 ACID 트랜잭션을 말하지만 구체적 보장은 시스템마다 다르며, Databricks의 트랜잭션도 다른 시스템과 다를 수 있다"고 덧붙입니다. 이 글은 **Delta Lake 기준**으로 설명합니다.

# 4. 원자성은 어떻게 구현되는가 (핵심)

공식 문서의 설명을 단계로 풀면 다음과 같습니다.

```
[1단계] 데이터 파일을 테이블 디렉터리에 쓴다           ← 아직 테이블에 "보이지 않음"
          part-0004.parquet, part-0005.parquet ...

[2단계] 모든 쓰기가 끝나면, 트랜잭션 로그에 새 항목을 "커밋"한다
          "버전 N+1: part-0004, part-0005 추가"        ← 이 순간 한꺼번에 보이게 됨
```

- 1단계 도중에 문제가 생기면(예: task 하나가 계속 실패해 job이 중단) **2단계의 커밋이 일어나지 않습니다.**
- 이미 써 둔 데이터 파일이 디렉터리에 남아 있어도 **로그에 없으므로 테이블의 일부가 아닙니다.** 그래서 테이블이 오염되지 않습니다.
- 이렇게 로그에 기록되지 않고 남은 파일은 나중에 **`VACUUM`** 이 정리합니다. (문서: "VACUUM은 실패한 트랜잭션에서 남은 미커밋 파일을 포함해, 테이블 디렉터리의 추적되지 않는 모든 데이터 파일을 삭제한다")

## 성공과 실패 시나리오

| 상황 | 1단계(파일 쓰기) | 2단계(로그 커밋) | 테이블에서 보이는 결과 |
|---|---|---|---|
| 모두 성공 | 완료 | **커밋됨** (버전 +1) | 새 데이터가 한꺼번에 보임 |
| 쓰기 도중 job 실패 | 일부만 씀 | **커밋 안 됨** | 이전 상태 그대로 (아무 변화 없음) |
| 커밋 시점에 충돌 감지 | 완료 | **커밋 거부** | 이전 상태 그대로, 쓰기 실패 |

## 우리 사례에 적용해 보기

Oracle에서 12개월 분량을 병렬로 읽어 **DataFrame 하나**로 만들고 한 번에 쓰는 경우를 생각해 봅니다.

```python
# 12개월이 하나의 DataFrame → write 한 번 → Spark job 하나 → Delta 커밋 한 번
df_12_months.write.format("delta").mode("append").saveAsTable("main.l0.orders")
```

```
1월 task ✓   2월 task ✗(끝내 실패)   3월 task ✓  ...  12월 task ✓
                     │
                     └─> job 실패 → 2단계 커밋 없음 → 12개월 전부 반영 안 됨
```

"2월만 실패했는데 왜 나머지도 안 들어가지?"의 답은, **커밋이 "12개월 전체"에 대해 한 번만 있기 때문**입니다. 버그가 아니라 원자성이라는 **기능**이 동작한 결과입니다. 일부라도 남기고 싶다면 **쓰기를 여러 번(= 커밋을 여러 번)으로 쪼개야** 합니다. (→ 청크 용어 글)

# 5. 트랜잭션의 범위: 무엇이 "하나"인가

- 기본적으로 **SQL 문 하나 = 테이블 하나에 대한 원자적 트랜잭션 하나**입니다.
- 그래서 아래 두 문장은 **서로 다른 두 트랜잭션**입니다.

```sql
DELETE FROM main.l0.orders WHERE order_dt >= '2026-01-01' AND order_dt < '2026-02-01';  -- 트랜잭션 ①
INSERT INTO main.l0.orders SELECT ...;                                                    -- 트랜잭션 ②
```

①이 성공해서 커밋된 뒤 ②가 실패하면, ①은 **되돌려지지 않습니다.** 결과적으로 "지우기만 되고 다시 채우지 못한" 상태가 됩니다.

- 여러 문장을 하나의 원자적 트랜잭션으로 묶으려면 `BEGIN ATOMIC ... END;` 구문을 쓸 수 있습니다. 모든 변경이 함께 성공하거나 함께 롤백됩니다.

```sql
BEGIN ATOMIC
  DELETE FROM main.l0.orders WHERE ...;
  INSERT INTO main.l0.orders SELECT ...;
END;
```

> 여러 **테이블**에 걸친 트랜잭션은 참여하는 테이블에 catalog commits가 활성화되어 있어야 하는 등 조건이 있습니다. 상세 조건은 공식 문서의 Transactions 페이지를 확인하세요.
{: .notice--info}

- 한 문장 안에서 "삭제 + 삽입"을 원자적으로 하는 가장 간단한 방법은 **`replaceWhere`** 입니다. (→ replaceWhere 용어 글)

# 6. 동시에 여러 작업이 쓰면? 낙관적 동시성 제어

Delta/Databricks는 **락(lock)을 쓰지 않는** 낙관적 동시성 제어(optimistic concurrency control)를 사용합니다. 그래서 읽기·쓰기에 락이 없고 **데드락이 생길 수 없습니다.** 대신 쓰기가 세 단계로 진행됩니다.

```
① Read              필요하면 테이블의 최신 버전을 읽어, 어떤 파일을 고쳐 써야 하는지 파악
                    (※ append-only 쓰기는 테이블 상태를 읽지 않음. 스키마 검증은 로그의 메타데이터 사용)
② Write             데이터 파일을 테이블 디렉터리에 씀
③ Validate & Commit 내가 읽은 시점 이후에 다른 작업이 커밋한 변경과 "충돌"하는지 검사
                    ├─ 충돌 없음 → 새 버전으로 커밋, 성공
                    └─ 충돌 있음 → 커밋 실패 (예외 발생)
```

"일단 하고, 커밋할 때 부딪혔는지 확인"하는 방식입니다. 서로 다른 파일을 건드리는 작업은 대부분 문제없이 함께 진행됩니다. 어떤 경우에 충돌하는지는 **격리 수준**, **Row-level concurrency** 글에서 자세히 다룹니다.

# 7. 일관성과 지속성

- **읽기**는 기본적으로 **snapshot isolation**입니다. 읽는 동안 다른 작업이 커밋해도, 읽기가 시작된 시점의 스냅샷을 일관되게 봅니다.
- 쓰기는 기본적으로 **WriteSerializable**로 격리됩니다. (→ 격리 수준 글)
- 여러 테이블을 읽는 쿼리는 **각 테이블의 "접근 시점 현재 버전"** 을 보며, 그 사이에 진행 중인 다른 트랜잭션을 방해하지 않습니다.
- **지속성**: 데이터 파일과 트랜잭션 로그가 모두 클라우드 객체 스토리지에 저장되므로, 커밋된 데이터는 그 스토리지의 내구성을 그대로 이어받습니다.

# 8. 직접 확인해 보기

각 커밋이 어떤 버전으로 남았는지는 히스토리로 볼 수 있습니다.

```sql
DESCRIBE HISTORY main.l0.orders;
-- version, timestamp, operation(WRITE, DELETE, MERGE, OPTIMIZE ...) 등이 한 줄씩 나옵니다.
```

실험으로 "쓰기 도중 실패 시 버전이 늘지 않는다"를 확인해 볼 수 있습니다. 일부러 실패하는 쓰기를 실행해 보고 `DESCRIBE HISTORY`의 최신 버전이 그대로인지 확인해 보세요.

# 9. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "일부 task만 실패했는데 왜 전부 롤백?" | 쓰기 한 번 = 커밋 한 번이라서. 정상 동작 |
| "DELETE 후 INSERT는 하나의 트랜잭션" | 각각 **별개** 트랜잭션. 묶으려면 `BEGIN ATOMIC` 또는 `replaceWhere` |
| "Delta는 락을 쓴다" | 락 없는 **낙관적** 동시성 제어. 커밋 때 충돌 검사 |
| "쓰다 실패하면 쓰레기 파일이 테이블을 망친다" | 로그에 없는 파일은 테이블의 일부가 아님. `VACUUM`이 정리 |
| "모든 DB의 ACID와 똑같다" | 시스템마다 구체적 보장이 다름. Delta 기준으로 이해할 것 |

# 10. 한 줄 정리

- Delta 테이블 = **데이터 파일 + 트랜잭션 로그**. 로그에 커밋된 파일만 테이블의 일부.
- 쓰기는 **파일 쓰기 → 로그 커밋** 2단계이며, 커밋이 되어야 한꺼번에 보인다. 그래서 **전부 성공 or 전부 실패**.
- SQL 문 하나가 트랜잭션 하나. 여러 문장을 묶으려면 별도 장치가 필요.
- 동시성은 **락 없는 낙관적 제어**로, 커밋 시점에 충돌을 검사한다.
